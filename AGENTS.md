# AGENTS.md: game-kit

For architects, build workers and reviewers of the owner's board-game adaptations. Read this, then the one catalogue entry and README of the component you touch. You should never need to read component source.

## What this is
Shared code, in a public repository (the games are private), for digital board-game builds: one best version of each reusable component (engine kernel, simulation, AI, saves, settings, UI frames, tooling, gates). Rules, card names, zones, texts and looks of any one game never live here. Index: [README.md](README.md). Catalogue of every component: [docs/CATALOG.md](docs/CATALOG.md) and the `needs` graph in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) (both generated by `node scripts/catalog.mjs`). Task guides: [docs/recipes/](docs/recipes/README.md). Never read the build plan (`docs/PLAN.md`) or `CATALOG.md` whole (both are large): `node kit.mjs search <word>`, then the recipe, then the README.

Open work: run `node kit.mjs state`.

Start by task ([recipe index](docs/recipes/README.md) has the paths): build a game: [new-game](docs/recipes/new-game.md), then [game-systems](docs/recipes/game-systems.md); change the kit: "Change the kit" below and [agent-workflow](docs/recipes/agent-workflow.md); checks, briefs and "done": [agent-workflow](docs/recipes/agent-workflow.md).

Needs Node 22.18+: tools run with plain `node` (no tsx, no build); relative imports name the `.ts`/`.tsx` file; no enums, namespaces or parameter properties (`erasableSyntaxOnly`).

## The locked copy (in a game)
- A game holds `kit/`, a copy of named components at a tag. **Never edit `kit/`**, never copy a component into `src/`, never port from an older game what the kit has.
- A game holds one kit tag. `node ../game-kit/kit.mjs pull ../game-kit <tag> [component...]` copies components (and their `needs`), moves the whole kit to that tag, and writes `kit/kit.lock.json` plus `kit/CATALOG.md`. Run `node kit/kit.mjs outdated` first ([upgrade-kit](docs/recipes/upgrade-kit.md)). `node kit/kit.mjs check` fails when `kit/` differs from the lock; every game runs it in its check chain. `node kit/kit.mjs check --source ../game-kit` also proves `kit/` matches the game-kit tag it names (fails if the tag moved).
- Before writing anything in a game: `node kit/kit.mjs search <word>`, then `kit/recipes/`, then the component README. `pull` copies `docs/recipes/` to `kit/recipes/`; `check` guards it like the rest.
- Inside a game, find what exists without the kit checkout: `node kit/kit.mjs list`, `node kit/kit.mjs search <words>` (titles, tags, looks, use, effect words, the parts inside big parts, and the mechanics map `kit/recipes/mechanics.md`: a mechanic prints first as `mechanic: <words> -> <answer>`, where the answer is the part and what to read, "partly" and what is missing, or "not in the kit"; a miss prints the nearest mechanics line and is logged to `~/.game-kit/search-misses.log`, newest: `search --misses`), `node kit/kit.mjs effects [words]`.
- Before adding a plan row, take its id with `node kit.mjs next-id --reserve` (in the game-kit checkout); it reads main and every open PR. The row is the file `docs/plan/K<n>.md` (front matter: `section`, then the table's columns such as `sources`, `effort`, `state`; the content line below it; copy a neighbour). Then run `node scripts/plan.mjs`: it writes `docs/PLAN.md` (generated, committed; never edit it by hand; on a merge conflict in it, resolve the row files and regenerate).
- Owner host and paths for phone serving live in an untracked `kit.local.json` (copy `kit.local.example.json`).
- Start a new game: `node kit.mjs new <dir> <id> "<Name>"` does it all (port block, repo, kit pull, first commit, GitHub repo).
- Workers: `node kit.mjs worktree` (or `worktree --here` when you already are in a worktree), `finish` and `teardown`; no install needed. `finish` (prints `PASS <sha>`; the reviewer checks it against the PR head) is for a game; for a row in this repository the proof is GitHub's check on the PR head, no `finish`. In a game, `finish` (without `--check`) first fails unless every file added under `src/` since the merge base with main (not tests or `*.d.ts`; more ignore globs in `package.json` `kit.builtNew.ignore`) is a line of the PR body's `## Built new` section (read with `gh pr view`, or `--body <file>` before the PR exists): `- <file or folder> | search: <words>; <other words> | nearest: <kit part or none> | why: <reason>` (K684). A moved or renamed file is not new. A folder covers its files only when it sits at least two levels below `src/` (`src/ui/motion/`); a `src/` or `src/ui/` line covers nothing. No merge base with main is a FAIL. `worktree --here` (the `node_modules` link) is not optional in a worktree: without it nothing resolves and the check fails. `next-id --reserve` holds the id.
- `reference-game` is the contract test of the kit's pieces; `card-parts` and `card-zoom`: the game owns its layout, the kit gives parts.
- Pulling a newer tag happens only when the game needs something in it. Commit `kit/`.

## Choose components for a new game
1. `search` / [CATALOG.md](docs/CATALOG.md): each entry says when to use it and when not. Effects: watch each one play in [gallery/effects.html](gallery/effects.html) (`node gallery/build.mjs` rebuilds it).
2. Read the component's README (its "Use it in 10 lines" is real, type-checked code) and, for `engine-core`, its guides (`timing.md`, `undo.md`, `random.md`, `legal.md`, `debug.md`).
3. `kit.mjs new` pulls the base set (`BASE` in `components/scaffold/scaffold.js`: engine-core, game-store, sim-pool, state-machines, app-frame, settings, saves, screens, lint-preset, ci-templates, check-runner, repo-gate, bundle-size); other tooling is pulled by hand (`--existing` for a repo that has files). Recipe: [new-game](docs/recipes/new-game.md).
4. Before using a part, read its "## Rules for agents" section (`kit/components/<name>/README.md` in a game) and follow every "You must".
5. A need the kit lacks: change the kit (below) or write "Kit gap" in the PR; do not fork.

## Change the kit
1. Look at open PRs: **one open PR per component**. Wait for or continue the one touching yours.
2. Branch `k<n>-<name>` from `origin/main` in a worktree of this repository. Add or find the row file `docs/plan/K<n>.md` (next free K number; set `state: done` in the same PR, then `node scripts/plan.mjs`; a component taken from a game also gets a line in `docs/SELECTION.md`, not enforced). Mark the row done in the same PR.
3. A bug: failing test first, then the fix.
4. Interfaces grow by addition; nothing breaking. A breaking change says `breaking` in its title and lists what a game must change.
5. New component: `components/<name>/` with `component.json` (`name`, `source.game`, `source.commit`, `source.paths`, `needs`), a README (non-empty first line), tests (a `*.test.*` or `test_*.py` file in the folder), and an entry in `docs/catalog-notes.json` (`use`, `not`). `npm run check` fails without them.
   A new component is also named by a line of `docs/mechanics.json` (`words` a planner types, `part`, `read`, `also`, `missing` for "partly", `row` for a candidate, `pending: K<n>` while an open row builds the part; no `part` means "not in the kit"; `sheet`: the id of the game-sheet question the line sits under, one of `SHEET_QUESTIONS` in `components/plan-checker/plancheck.py`, the nearest one when none fits), or its entry says `"mechanics": "none: <reason>"` (tooling, screen parts); a candidate row says `mechanics: none: <reason>` in its front matter. `node scripts/mechanics-check.mjs` (in `components:check`) fails otherwise, fails a line with no `sheet` key or an unknown one, fails a pending line whose row is done, fails a backticked name in `read` that is not an exported name of the part, a member of one of its exported types, or one of its files (tests, comments and README prose do not count), and runs the fixed `searches` of that file. A part inside a big part gets its own entry under the key `<component>/<part>` (`title`, `tags`, `use`, `guide`: a file in the component folder); it prints under its component in `CATALOG.md` and `search` returns it with its guide.
   Every component entry also carries `title` (up to 8 plain words), `tags` (3 or more plain words a person would type), `visible`, `release` (1.0, 1.1 effects, 1.2 sound, 1.3 voice), `gameSupplies` (one line) and, if seen on screen, `looks` (one sentence). A new component arrives with all of them; `node scripts/catalog.mjs --check` fails without. Naming rules: the id or title says what the player sees; the purpose goes in `use`, not the name; use words a director would type: no game's name, no building word (canvas, radial, pool), no rare word; two or three words for an id, 20 characters at most; one look per entry. `release` is the first game release that uses the part. A part with motion that games run at speed 0 in 1.0 (hand, pile, track, counter and the like) is 1.0. 1.1 is for parts that exist only for effects, 1.2 for sound and music, 1.3 for voice.
6. README: purpose in the first line, a **Use it in 10 lines** section (from the component's own tests or types; never an invented API; `scripts/readme-examples.mjs` type-checks every TypeScript one in `npm run components:check`).
7. Every change that adds, renames or changes how a component or tool is used updates that README's "## Rules for agents" section in the same PR, true to the code; a reviewer fails a PR that does not. `npm run components:check` fails a README without that heading.
7a. Every PR that adds or changes a part adds its three searches to `docs/search-cases.json` (`{ "q": "<plain words>", "first": "<part, part/sub, effect id or K<n>>" }`, or `"first": "none"` for "not in the kit"); `node kit.mjs search --check` (in `components:check`) fails each case whose first line does not name it.
7c. A component a game can go around (do by hand what its hook does) declares the ways in `component.json` `bypass`: `[{ id, imports?, match, flags?, hook }]` (`imports`: component names, one of which a `src/` file must import, default the component itself; `match`: a regex on the file; `hook`: what to use instead). `kit.mjs check` in a game fails each match as `file:line id (component): hook`, unless the line or the one above has `// kit-allow <id>: <reason>`.
7b. A new effect arrives with its catalogue entry, demo and strip (`node gallery/build.mjs --strips`; the PNGs go in `gallery/strips`). Specs use the new effect ids; old ids (effect-library README, "Old ids") keep working forever. A name changes in a spec only when that spec is edited for another reason.
8. Done = independent review and GitHub's check green on the PR's head commit (the kit's CI runs on GitHub-hosted machines on every push to a PR, drafts too); the steward then lands it with a merge commit. Then an annotated tag on main (`git tag -a <v> -m <v>`): **middle number up for a feature or new component, last number up for a fix**. Draft PR, no hooks, never merge your own batch.

## Rules agents break most
- Editing `kit/` in a game, or copying kit code into `src/`.
- A `'..'` or `'../x'` string in a component code file that leaves the component folder for a component not in its `needs` (`scripts/check-components.mjs` flags it); use `dirname()`.
- Importing a kit component from another without listing it in `needs` (same check).
- `async` functions without `await` (lint `require-await`), tests included.
- A "Use it in 10 lines" block that no longer compiles (`scripts/readme-examples.mjs`).
- Deciding a game rule or a look yourself: ask the arbiter or director session, or write it in the PR ("Rules questions", "Look questions", "Kit gap").
- Showing rule ids (`TURN-07`, `AR-12`) on screen: use `plain-text`.
- Reading hidden state in an opponent (see below).
- Unseeded randomness in an engine (`Math.random`, clock): only `ctx.rng` (a game's `lint-preset` fails it).
- Editing `docs/CATALOG.md`, `docs/PLAN.md` or `docs/recipes/mechanics.md` by hand: run `node scripts/catalog.mjs` / `node scripts/plan.mjs` (`components:check` fails when stale).
- Running heavy tests locally on Windows.
- Inventing a port, or hard-coding one that is not in `ports.json` (see "Ports" below).
- Re-reading files or pictures already in context; repeating a failed call unchanged (three strikes, then stop and report).

## Where tests and CI run
- Never heavy tests on local Windows. CI and the full gate run on the self-hosted runners (WSL, labelled per game); this repo's CI runs on GitHub-hosted ubuntu-latest; to fall back to the PC runner set the repo variable KIT_RUNS_ON to ["self-hosted","kit"]. Local checks: only the ones you touched (types, lint, the test file).
- Here: `npm run check` = lint, typecheck, vitest, `components:check` (component rules; `CATALOG.md`, `ARCHITECTURE.md`, `PLAN.md` and the mechanics map current; the mechanics gate; README examples type-check). What each catches: [agent-workflow](docs/recipes/agent-workflow.md). Worktrees lack `node_modules`: link them from another checkout, never commit them.
- A game's gate comes from `ci-templates`; its check chain from `check-runner`.

## Ports: one source of truth
- Every port used by a game, tool, test or agent comes from [`ports.json`](ports.json) (readable view: [docs/PORTS.md](docs/PORTS.md), generated). Never invent one.
- Each game owns a block of 10 from 6010: dev = block, preview = +1, e2e = +2, second e2e = +3, the rest spare. 4170-4199 is phone serving only; 5190-5299 is Codex worktree servers; CI picks a free port.
- A new game gets its block with `node tools/game-server/server.mjs add <id> "<Name>" <repo path>`; it prints what to set in vite and Playwright. Commit `ports.json` and `docs/PORTS.md` here.
- Any port change goes into `ports.json` first (validated on load by `validatePorts` in `tools/game-server/lib.mjs`), then into the game. More: [tools/game-server/README.md](tools/game-server/README.md).

## Owner's standing rules that touch code
- **Never prettify**: no reformatting, tidy-ups, renames for style, decorative comments or docstrings. Shortest correct code; change only what the task needs.
- **No hooks** unless asked.
- **No old-save work** in any game until it is complete.
- **Opponents decide from the player's own view** only: `redact`, no hidden state of the real game; a greedy that reads it is a test pilot.
- Screen text matches what the engine does; fit text, never drop it. No rule ids on screen.
- Release ladder: 1.0 no animation or sound; 1.1 VFX; 1.2 SFX and music; 1.3 voice.
- The games' repositories are private and never deployed publicly. This kit is public: nothing personal goes into its code, docs, rows, commit messages, PR titles and bodies or tags (no person's name, e-mail address, local drive path, session or chat link, no game's card text); commits use a no-reply identity; `npm run personal` is part of the check. GitHub files under 50 MB.

## Reports
Short: the batch id, PR number, branch, check result, what now works, count of open questions. Post-build notes go in `docs/post-build/notes/`.
