# Start a new game on the kit

For a specification-driven local start, run `node kit.mjs spec resolve <spec.json> --ref <tag>`, register the destination with `node tools/game-server/server.mjs add <id> "<Name>" <dir> --pending` if needed, and run `node kit.mjs spec generate <spec.json> --dir <dir> --ref <tag>`. Profiles select components; an explicit supported `assembly` supplies executable rules and adapters. Generation publishes the new scaffold after its pinned components, lock and installation succeed. In the generated directory, run `git init`, `git add -A` and `npm run check` for baseline validation. `--link` lets you use existing local dependencies, which the generated ignore keeps out of Git. The assembly record keeps configuration validation separate from bootstrap and gameplay checks that have not run. [Declarative starter](../../components/scaffold/README.md#declarative-starter-k551-first-increment)

The [courier assembly](../../components/scaffold/README.md#bounded-courier-assembly) supplies its declared movement rules, setup, store, public-view pilot, saves and UI. Supply its grid, pickup/destination, movement allowances and authored winning route. It wires plan-checker, traceability, plain-text and theme-check for that bounded noncard contract. Run its generated `npm run test:acceptance` for real gameplay and browser evidence. A profile-only starter still needs game rules, adapters and the game-specific gate inputs below; choosing a card profile does not create a playable card engine. The [bounded reference card assembly](../../components/scaffold/README.md#bounded-reference-card-assembly) supplies a second executable composition: approved immediate-hit records plus Rally, Ward and Mend, independent printed expectations, life totals, rounds and difficulty. Run its `test:bootstrap` for non-browser checks and `test:acceptance` for the additional real browser milestone. Both use the existing execution receipts; verify current source/spec/lock/acceptance bindings before reusing a result. Read the [reference game's loaded-content acceptance](../../components/reference-game/README.md#bounded-executable-acceptance) for its exact semantic boundaries.

1. **Start in one step:** `node ../game-kit/kit.mjs new <dir> <id> "<Name>"` registers the port block, writes the repo, pulls the kit, makes the first commit and creates the private GitHub repo with delete-branch-on-merge; re-running skips what is done, `--no-remote` skips the first commit and GitHub operations. A new directory can still get `git init`; `--existing` is for a repo that already has files and history: it writes only new files, lists any clash and writes nothing, and commits nothing. Then commit `ports.json` and `docs/PORTS.md` in game-kit. Steps 3-4 below are then partly done: only add what `new` did not.
2. **Find components.** Read the short table at the top of `kit/CATALOG.md` (one line per component), then `node kit/kit.mjs search <word>` and the entry's "Use it when / Not for". Why a component comes from the game it does: [SELECTION.md](../SELECTION.md) (only when choosing between two). Every game starts with `engine-core` (it is the engine), `game-store` (one `defineGame` object, one store: [game-store](game-store.md)), `state-machines`, `app-frame`, `settings`, `saves` and `sim-pool`. A card consumer also uses `card-harness` for tests on its actual cards; noncard games declare the applicable rule and scenario evidence without inventing card sections. Which component serves which game system: [game-systems.md](game-systems.md).
3. **Pull the tooling.** `new` pulls `engine-core`, `game-store`, `sim-pool`, `state-machines`, `app-frame`, `settings`, `saves`, `screens`, `lint-preset`, `ci-templates`, `check-runner`, `repo-gate`, `bundle-size` and their needs, and wires `repo-gate` and `bundle-size` into the check chain. It does not pull or wire `plan-checker`, `traceability`, `theme-check` or `plain-text` (the generated `CLAUDE.md` lists them as TODO): pull them by hand with the command below and add their lanes to `scripts/check-runner.config.json` (each needs the game's own settings).
   ```bash
   node ../game-kit/kit.mjs pull ../game-kit <tag> engine-core sim-pool saves settings app-frame
   node kit/kit.mjs check
   ```
   `pull` adds each component's `needs`; a game holds one kit tag (a later `pull <tag>` moves all of it; `outdated` shows what changed). Commit `kit/`. Never edit it (see [AGENTS.md](../../AGENTS.md)).
   **Ports** (by hand, if not using `new`): take the game's port block: `node ../game-kit/tools/game-server/server.mjs add <id> "<Name>" <repo path>`. Set vite `server.port`, `preview.port` and the Playwright port to what it prints; commit `ports.json` and `docs/PORTS.md` in game-kit. Never invent a port ([PORTS.md](../PORTS.md)).
4. **Write the game's engine** against `engine-core` (`new` leaves a stub `GAME_DEF = defineGame(...)` in `src/engine/rules.ts`, a store in `src/ui/store.ts`, menu, set-up, play, settings and saves routes in `src/ui/App.tsx`: replace the stub, keep the shape): a `GameTypes` bundle and one `GameRules<G>` (`handlers`, `blank`, `setup`, `contentHash`, optional `stamp`, `invariants`, `revealWords`). The smallest model is `components/engine-core/fake/counter.ts`; a card game with turns, triggers, an automa and a campaign is the reference game (the canonical `components/scaffold/reference-cards/` overlay and `components/reference-game/template/` compatibility tests in the kit checkout; map: [game-systems.md](game-systems.md)). Import from `kernel.ts`, `timed.ts` (timing) or `tools.ts` (tests, sims, debug), or `index.ts` (all three).
5. **Wire the check chain** with `check-runner`: `new` has lanes for lint, types, tests, `kit.mjs check`, `repo-gate`, `bundle-size`; add `traceability` and the others by hand. CI comes from `ci-templates` (`ci.config.json`, `render.mjs`), never hand-written.
6. **Add the sim module** (`simGame = simGameOf(GAME_DEF, ...)` from `game-store/sim.ts`) as soon as one prompt can be answered, so fuzz catches engine bugs from day one ([simulations.md](simulations.md)).
7. **Screens**: `new` wires `app-frame` routes, `screens` (menu, set-up), `settings` schema and `saves` over engine-core's save file; the game fills in its own ([saves-settings-frame.md](saves-settings-frame.md)). The look comes from the director's wireframes and the game's token file, never from guesses.
8. **Rules and looks are never decided by you.** Ask the arbiter or director session, or write the question in the PR.

Proof it works: `node kit/kit.mjs check`, then the game's own `npm run check` on the self-hosted runner (`node kit/kit.mjs finish` runs it there: [agent-workflow.md](agent-workflow.md)).
