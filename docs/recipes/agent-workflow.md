# Work as an agent in this repo

Use when you are a worker given one batch. The order below is the order of use. The worker scripts are `scripts/agent.mjs`; `kit.mjs` is at the root of a kit checkout (pulled into a game as `kit/kit.mjs`, with `kit/agent.mjs` beside it: `node kit/kit.mjs worktree|finish|teardown` works in a game, using the game's own `npm run check`; tried on 7th Inning Stretch).

1. **Id.** A new plan row is a file `docs/plan/K<n>.md` (copy a neighbour; then `node scripts/plan.mjs` regenerates `docs/PLAN.md`) and needs a free number: `node kit.mjs next-id [n] --reserve` reads origin/main, every open PR's `docs/plan/` file names and the reservations, then reserves the id(s) by pushing `refs/kit-reserved/K<n>` to origin (only if absent, so two sessions cannot get the same one before a PR exists). Run it before you write the row.
   On a `docs/PLAN.md` conflict take either side and regenerate it with `node scripts/plan.mjs`.
2. **Worktree.** `node kit.mjs worktree --branch <name>` makes a worktree from origin/main and links `node_modules` (a junction on Windows, kept out of git). With no `node_modules` anywhere it says to `npm ci` or pass `--shared <base>` (in WSL `~/codex/<key>-base`). Already inside a worktree the harness made for you: `node kit.mjs worktree --here [--branch <name>]` only links `node_modules` (from the main checkout, or `--shared`) and switches to the new branch. No install and no tsx needed. Work only in that worktree.
3. **See the state.** `node kit.mjs state` (kit checkout) prints the PLAN rows not done, what waits, the open PRs with the component each touches, each game's oldest kit pin against the latest tag, and what to watch. In a game, `plancheck.py --batch <id>` gives your batch's line ranges; read only those. The plan checker also warns (never fails) when the game's kit pin is 5 or more minor versions behind the latest tag, or a `Phase GK` targets a K row the kit marks done: pull the newer tag or drop the phase.
4. **Build.** Commit at each milestone. Run only your own checks.
5. **Finish.** In a row of this repository there is no `finish`: push, open the draft PR, and the proof is GitHub's check (`npm run check`) green on the PR head commit; it runs on every push, drafts too, but a PR that conflicts with main gets no check at all until main is merged into the branch (`git merge origin/main`). In a game: run it from Windows node in the worktree (not from inside WSL: a Windows worktree's `.git` path does not resolve there). `node kit.mjs finish [--repo <worktree>] [--check 'npm run check'] [--comment]`: exit 1 on uncommitted changes or a detached HEAD, else it clones the branch in WSL (own TMPDIR beside the clone; no WSL means FAIL with the reason, never a local run), installs, runs the check there and prints `PASS <full sha>` or `FAIL <full sha>` first, then the tail; With `--check` the line is `check passed <sha> (check: <command>)` (or `check failed`), never `PASS`, so it cannot pass for the gate. `--comment` posts that line on the PR. A reviewer compares the sha with the PR head (`gh pr view --json headRefOid`) and rejects a missing or older one. Then push and open the draft PR.
   While the queue holds a waiting or running job `finish <branch>`, a second `finish` is refused (exit 3, the job named): never start another, read the first; so is one whose result folder shows a run with a heartbeat less than 2 minutes old. It prints `queued, N ahead` or `running, mm:ss` about once a minute on stderr (stdout carries only the result). When the call may outlast your tool's ten-minute limit, run `node kit.mjs finish --detach [same flags]` (returns at once, prints the result folder under `~/.game-kit/finish/`), then `node kit.mjs finish --result [--comment]` now and then: exit 4 with the status line (stderr) while it runs, else the stored `PASS <sha>`/`FAIL <sha>` output and its exit code; exit 5 `STALE` when the stored result is for another commit than the run's head. The run writes a start marker first; if it is missing after 45 s (the WSL launch from Git Bash, PowerShell or WSL did not take), `finish` exits 6 with one line `the run did not start` and the exact command to run by hand (`wsl -e bash -c "bash '<run.sh>'"`, the same text in PowerShell and Git Bash), never waiting silently (K644). A plain `finish` cut off by a timeout keeps running; `--result` reads it too.
6. **Teardown** after the merge: `node kit.mjs teardown --worktree <dir>` cuts the link (never its target), then removes the worktree. `--force` discards uncommitted changes: only on purpose.

## Checks and what each catches
In this repo `npm run check` (CI runs it through `check-runner`):
- `lint`: ESLint with type-checked rules (`require-await`, no `any`, type imports).
- `typecheck`: `tsc -b`, including components' tests.
- `test`: vitest, every component's tests and `tests/` (the reference game is generated and checked by `components/reference-game/reference.test.ts`).
- `components:check`: `scripts/check-components.mjs` (`component.json` fields, existing `needs`, README first line, a test file, and the module and path checks below); `scripts/catalog.mjs --check` (`CATALOG.md`, `ARCHITECTURE.md`, `PLAN.md` current, a `catalog-notes.json` entry per component); `scripts/readme-examples.mjs` (every "Use it in 10 lines" block type-checks).

The component checker uses the installed TypeScript parser. Declare the npm package name in `component.json` `packages` for literal JS/TS imports, re-exports, dynamic imports, and `require()` calls. A scoped subpath such as `@scope/package/feature` uses `@scope/package`. Node built-ins and test-only sources use their existing exemptions. The checker identifies the file, line, column and declaration to add.

Parent-relative literals also require a `needs` entry when they refer to another component. That check includes asset URLs, stored paths, test files and TypeScript path references. Ordinary comments and the first message argument of a directly thrown `Error` call are exempt. Computed module names, alias resolution and package installation are the caller's responsibility. Keep dependencies of standalone tooling out of consumer manifests. The checker handles the existing Playwright screenshot dependency only at `phone-mode/demo/imp-shots.mjs`.

In a game made by `kit.mjs new`, `npm run check` runs `scripts/check-runner.config.json`: tests, lint (`lint-preset`: pure engine, no `Math.random`, UI imports the engine only through `src/engine/api.ts`), types, `kit:check` (`kit/` equals the lock), `ci:check` (workflows equal the template), `repo-gate` (file sizes, secrets, hosts, card names in rules code), build, `size` (`bundle-size`). Added by hand per game: `traceability` (tests cite rule ids), `theme-check`, `plain-text`, `plan-checker`.

## Brief a worker
A bounded generator turns explicit task decisions into a pinned brief:

```sh
node tools/kit-context/brief.mjs task.json --game ../my-game --source . --max-chars 24000
```

Use the [task schema and continuation contract](../../tools/kit-context/README.md#bounded-worker-brief). Supply the authorized owned/proposed files, required API contracts, rule/look questions, exact kit commit and registered acceptance scripts. The result fingerprints declared inputs, preserves unresolved questions and leaves command execution false. Follow every required continuation; a complete packet does not establish task readiness or passing acceptance. Regenerate and compare fingerprints after changing task, files, scripts or kit pin.

For an approved executable assembly, use `brief.mjs --assembly` with explicit decisions and its current specification/manifest. Opt into focused public-API context at the installed pin; consume all continuation pages and named dependency/manual reads. Changed source and task inputs invalidate old fingerprints. Versioned component observations can accompany context from an explicitly supplied local inventory; test-file presence, executed reference checks and authorized production use remain separate. [Context and observations contract](../../tools/kit-context/README.md)

Measure a nominated worker task with a protocol declared before handoff and the [record-traced observation importer](../../tools/reuse-metrics/README.md). Keep missing usage/cost/baseline data missing. An actual receipt confirms recorded command execution and input matching; independent rules and playable endpoints need their own review.

A worker starts with a fresh context. The brief stands alone when it names:
- the repo, the branch `k<n>-<name>` (or the game batch id) and the row id, already reserved;
- the files or plan line ranges to read (never "read the plan"), and the recipe;
- what done looks like: the test that proves it, and, in a game, `finish` printing `PASS <sha>` (in this repository, GitHub's check green on the head commit);
- what is out of scope, the arbiter or director session for questions, and the size at which to stop and report.

## Before you say done
- `git status` clean, every change committed and pushed; in a game the PR head equals the sha in the `PASS` line; in this repository every check on the PR is green for the head commit.
- The new test was seen failing without the change.
- Existing callers behave as before unless they opt in, and a test shows it.
- Exit codes are asserted, not only printed text.
- The whole check is green on the head commit.
- The behaviour is shown by a test that failed before (a bug) or by real data (a run, a screenshot), not by reading the code.
- Generated files regenerated, not edited: `node scripts/catalog.mjs`, `node scripts/plan.mjs`.
- The row file says `state: done`; open questions are in the PR body ("Rules questions", "Look questions", "Kit gap").

Pitfalls
- Never run the heavy check on local Windows; in a game `kit.mjs finish` runs it in WSL.
- `worktree --here` (the `node_modules` link) is not optional in a worktree: without it nothing resolves and the check fails.
- Do not copy `node_modules` into the worktree and do not commit the link.
- `next-id` needs `gh` signed in to see open PRs; re-run it just before you open the PR if the batch was long.
- `kit/` in a game changes only by `kit.mjs pull` (see [new-game.md](new-game.md)).
- Recipe links to `../../components/<name>/README.md` work in the kit checkout; in a game read `kit/<name>/README.md`.
- Reading `docs/PLAN.md`, `CATALOG.md` or `SELECTION.md` whole burns the budget: `kit.mjs state`, `kit.mjs search`, then one entry.
- `finish` clones the committed branch: uncommitted work is not checked, and it refuses to run on a dirty tree.

Proof: in a game, `finish` prints `PASS <sha>` for the PR head; in this repository, GitHub's check is green on the PR head.

## What finish checks

`finish` (prints `PASS <sha>`; the reviewer checks it against the PR head) is for a game; for a row in this repository the proof is GitHub's check on the PR head, no `finish`. In a game, `finish` (without `--check`) first fails unless every file added under `src/` since the merge base with main (not tests or `*.d.ts`; more ignore globs in `package.json` `kit.builtNew.ignore`, each `{ "glob": ..., "why": ... }` with a non-empty why, at most 10, none covering most of `src/` such as `src/**` or `src/**/*.ts`) is a line of the PR body's `## Built new` section (read with `gh pr view`, or `--body <file>` before the PR exists): `- <file or folder> | search: <words>; <other words> | nearest: <kit part or none> | why: <reason>` (K684). A moved or renamed file is not new. A folder covers its files only when it sits at least two levels below `src/` (`src/ui/motion/`); a `src/` or `src/ui/` line covers nothing. No merge base with main is a FAIL. A new top-level export (function, class, enum, const, destructured const, default, hook) or a new top-level `setTimeout`/`setInterval`/`createMachine` added to a changed `src/` file needs a line too, naming `<file>#<export>` or the file; renaming or editing an existing export does not count. `finish` runs each line's two searches again with the game's `kit/kit.mjs search`: when a search's first 3 lines name parts and none of them is the line's `nearest` (or any part when it says `nearest: none`), it fails as `check: search finds <part>`; use that part, or name it as nearest with a why (K688). When the branch adds or changes `docs/experience/**`, `docs/BUILD_PLAN.md` or `docs/handoff/**` (more globs in `package.json` `kit.claimDocs`, never fewer), every added or changed line there that claims the kit lacks something (not in the kit, the kit lacks, kit has no, kit ships no, not covered by the kit, build our own and the like; "kit gap" not followed by closed/done; a leading `Gap:` label, not CSS `gap: 8px`; a `Built new:` label or a list item under a Built new heading; "new effect" only with a lack phrase; "game-own" only "instead of the kit"; fenced code, inline code, `>` quotes, `[x]` items and headings skipped) needs `search: <words>; <other words>`; each phrasing runs with `kit/kit.mjs search` and `effects`, and when their first 3 lines name a part or effect the line needs `nearest: <that part> | why: <six words or more>` (`check: search finds <part>`); a K<n> on such a line whose row is done in the kit fails (`the kit row is done: pull it`) (K698). `node kit.mjs claims <file> [--repo <game repo>] [--before <old file>]` runs the same claim rules on one file as it is on disk, any path (`--before`: only lines new or changed against the old file; a missing old file means all lines; no `--repo` or not a git repo: the repo is found from the file; no `kit/` there: the game-kit checkout's kit.mjs; no kit: only the search-line rule): exit 1 on claim problems, 2 on usage or a missing file, 0 when clean or empty. `worktree --here` (the `node_modules` link) is not optional in a worktree: without it nothing resolves and the check fails. `next-id --reserve` holds the id.

- K712: a PR body's `Must use: <part>:<export>` line is checked against src/ imports (only `Waived: <part> | architect | why` clears one); each Kit gap line needs `readme: "<line>"` and `tried: <case> -> <result>`; finish prints ORDERS n/m; e2e runs whenever a browser path changed (see K754 below). K715: an entry with no `:<export>` fails (a bare part passes on any import, so a skipped export goes unseen); write `<part>:*` for a part used whole. K717: a part whose component.json says `"testOnly": true` (card-harness, test-setup) is found in src/ or tests/ (test files and local re-exports count); every other part only in src/
- K754: full `finish` selects e2e when changes match `src/ui/**`, `src/main.tsx`, `index.html`, `src/screen/**`, `src/app/**`, or a directory added in `package.json kit.e2eRoots`. A move checks both its old and new paths. List additional directories as repository-relative names using `/`, for example `["frontend/table"]`. The command comes from `kit.e2e`, `e2e`, or `test:e2e` and `test:e2e:phone`. If you upgrade an existing game without a browser command, register a runnable suite before finishing a UI batch. Use `finish --check "<command>"` for an explicitly scoped engine check.


## Coverage evidence

The kit's existing hosted test run produces the V8 JSON summary. `npm run coverage:table` reads it once, reports covered/total lines and branches per component, and writes `coverage/coverage-evidence.json` plus a Markdown table. Percentages are computed from summed counts, not averaged file percentages. Zero branches means `n/a`. Only reported component TypeScript files are included; omitted files and components are not silently treated as covered.

CI first runs `node scripts/coverage-table.mjs --capture "$RUNNER_TEMP/game-kit-coverage-start.json"`. It validates a destination outside coverage, including path aliases, before clearing prior coverage and saving actual Git HEAD/tree and the reporting tool's digest. Capture protects tracked files and allows replacing only a previous context at an unaliased regular file. After the existing check, including failure, it runs the reporter with `--started` and the check step's actual `--check-outcome`. The reporter requires an unaliased regular context file, checks both report paths before replacing either, and validates the coverage directory identity before staging and publishing. It refuses aliases, tracked paths and directories at either report path. The report retains the raw summary digest, repository-relative source hashes, configuration hashes, runtime, run identity, dirty-source indication and source binding. A dirty or changed source, malformed/missing context, or summary predating capture cannot be matched evidence. Artifacts are named by the actual checked commit and run attempt and retained for 30 days. This does not run the test suite again.

Every reported source and configuration file must be a regular tracked blob at the captured commit with matching bytes. The reporter also checks the full tracked checkout against that tree with a fresh temporary Git index and requires the raw `workingSha256` fingerprint to match from capture to report. Git can normalize line endings and filtered files for the tree check, while the fingerprint records their checked-out bytes. Ignored generated files, symlinks and content changes hidden by Git index flags or cached timestamps cannot produce a matched binding. The coverage summary must be an unaliased regular file. Missing coverage is `unavailable`; malformed counts and aliased summaries are `invalid`. A failed, cancelled or skipped check stays labelled as such even if a partial summary exists. Standalone reporting without a before-run context records unknown execution and unavailable binding. `--check-outcome` requires `--started`. Coverage counts establish neither rule correctness nor completion of a particular acceptance scenario.

**Policy for changes to critical components:** when changing engine-core, game-store, sim-pool, card-language, card-harness, scaffold or their shared adapters, inspect the affected components' line and branch counts and the relevant behavioral/negative tests. CI selects the newest retained successful main-push ancestor from the latest 100 successful runs of this workflow. It checks run identity, attempt, ancestry and artifact digest before passing the raw summary and payload to `coverage-table.mjs --baseline <directory>`. A name alone never qualifies an artifact. A missing retained ancestor leaves the comparison unknown.

The comparator independently verifies both payloads against their respective commit trees, complete configuration inventories, source/configuration blobs, reporter bytes and raw summary digests. It also requires a selected run, matching artifact metadata, the retained archive SHA-256 and byte-identical extracted report members; Python 3 reads only the two named ZIP entries. Different source bytes across the two revisions are expected. Comparison requires the same declared scope, reporter, configuration/dependency hashes and Node version; changed instrumentation remains incompatible. Weighted component deltas retain covered/total counts, percentage-point changes, added/removed or omitted files, and zero-denominator `null` values. Component losses remain visible even if another component improves. Scope changes do not establish no regression. Missing, malformed, stale, failed or unverified evidence leaves regression status **unknown**. Comparisons are informative; no blocking threshold or rule-correctness claim follows from a coverage percentage. Coverage does not establish adoption, maturity or development cost.

Read observed-scope deltas and like-for-like deltas separately. The like-for-like subtotal requires identical source bytes and equal positive denominators for each metric. The JSON report names the files left out and distinguishes Git additions and removals from changes in instrumentation. A partial subset can expose a loss while the rest of the component remains unknown. The [coverage-table guide](../../tools/coverage-table/README.md) documents the output and retained main-run replay.

## Platform case evidence

The focused hosted Windows lane runs the three art-publication path aliases, the coverage-directory case alias and the protected brief-directory alias. `node scripts/platform-cases.mjs windows <new-report.json>` checks the actual JSON test results and fails if any required case is absent, skipped, duplicated or failed. Its report includes the checked commit, each executed case and a clean tracked-source fingerprint matched before and after the command. A configured lane is not evidence that it has passed; inspect the artifact and required check on the final PR head.

The separate PDF capability lane installs pinned optional PDF/canvas dependencies and executes the real rendering case. Its report records package versions. The ordinary Ubuntu check and native Chromium suite remain in place. A missing browser or PDF capability must remain unexecuted evidence, and a newly exposed Windows defect remains open until its repair passes the same cases.

## Catalogue entry fields

Every component entry also carries `title` (up to 8 plain words), `tags` (3 or more plain words a person would type), `visible`, `release` (1.0, 1.1 effects, 1.2 sound, 1.3 voice), `gameSupplies` (one line) and, if seen on screen, `looks` (one sentence). A new component arrives with all of them; `node scripts/catalog.mjs --check` fails without. `hooks` (K685, optional): one `name + name: what it does, in plain words` line per hook a game calls, each name a code span of its README; `search` prints a matching line under the component and scores its words as title words, and `catalog.mjs` writes them as the block between `<!-- hooks: ... -->` and `<!-- /hooks -->` at the top of the README's "Rules for agents" (never edit the block by hand). Naming rules: the id or title says what the player sees; the purpose goes in `use`, not the name; use words a director would type: no game's name, no building word (canvas, radial, pool), no rare word; two or three words for an id, 20 characters at most; one look per entry. `release` is the first game release that uses the part. A part with motion that games run at speed 0 in 1.0 (hand, pile, track, counter and the like) is 1.0. 1.1 is for parts that exist only for effects, 1.2 for sound and music, 1.3 for voice.
